# Better Codex 当前开发路线图

更新日期：2026-08-25

本路线图只保存在本机 `plan/`，不进入 Git，不作为公开承诺。当前状态以仓库、发布资产、真实桌面验收和 Better Codex 看板为准。

## 产品目标

Better Codex 是运行在 Codex Desktop 内的本地优先任务看板与多 Agent 协作系统。近期目标不是继续扩充功能数量，而是让任务创建、执行、补充消息、状态判断、会话交接、更新和恢复形成稳定闭环。

核心主张：

> Chats are not a workflow.
>
> Codex writes code. Better Codex keeps work moving.

## 当前基线

- 当前 main 源码版本已到 `v0.4.2`；发布资产、安装态和真实桌面状态仍需分别核验。
- macOS 与 Windows 已有 Preview 安装入口、签名校验、更新通道和回滚基础。
- 看板、Project、Issue、Agent、自动调度、人工审核、归档、通知、Mockup 和本地 MCP 已经可用。
- 官网与使用文档已经上线，公开反馈入口已经出现真实用户 Issue。
- 当前最大工程风险是任务执行与 Codex 原生 Session 的状态、输入权和中断权没有完全统一。
- 本地看板仍有已实现但未验收、已完成但未关闭的状态债务。
- 本地 Web UI 与 Self-hosted Hub 已有独立原型，但 Web 工作区尚未提交，旧 Hub 分支也落后于当前 main，不能直接合并。

## 执行原则

- 先完成当前 Session、Run、安装和恢复稳定性收口，再启动新的大型功能。
- 代码完成、CI 通过、发布资产存在和真实桌面可用是四个独立证据层。
- macOS 与 Windows 同级支持；跨平台能力必须分别验收。
- 保持本地优先。默认不上传 Issue、对话、代码、文件、附件、日志和环境变量。
- Runtime、数据库和领域状态不依赖某个 Codex DOM 版本；CDP 只作为宿主适配层。
- 多 Agent 已是现有能力，近期工作是可靠性验收，不再把它当作遥远的新功能。
- Preview 可以快速迭代；Stable 只接收完成安装、升级、回滚和真实桌面验收的版本。
- 安装者不需要预先准备开发环境。系统 Node 依赖必须由安装器检测，并在需要安装或升级时取得用户确认。
- 每个里程碑独立交付；后续计划暂停时，已发布版本仍然可用。

## P0：当前稳定性收口

### 当前任务

1. 完成原生 Session 执行与控制权改造，统一首次执行、后续 turn、运行中 steer、中断和原生会话交接。
2. 以真实 Session 状态决定卡片输入框是否可用，避免把已送达消息误判为失败。
3. 验证 Runtime、Codex 和注入层重启后的 Session 恢复，不重复执行、不丢失最终回复。
4. 集中验收并清理 BET-135、BET-136、BET-151、BET-153、BET-158 的看板状态。
5. 在 macOS 与 Windows 分别验证 Preview 安装、重装、升级、回滚、禁用和卸载。
6. 只有上述路径对同一个当前候选 SHA 完成后，才推进 Stable。

### 完成门槛

- 创建 Agent Issue 后可以在同一 Codex Session 中持续执行，不依赖独立的 `codex exec` 子进程维持会话。
- 运行中补充消息、等待审批、等待用户、空闲、失败、断连和中断都有唯一且可恢复的状态。
- 卡片与 Codex 原生会话不会同时持有写入权；交接行为和下一步入口清晰。
- Runtime 或 Codex 重启后，已开始的任务不会被错误标记为新任务、完成或失败。
- 同一请求重试不会创建重复 turn，也不会重复改变 Issue 状态。
- Preview 安装资产能在 Apple silicon、Intel macOS 和 Windows 用户环境中完成真实安装与重装。
- Stable 发布前不存在未解释的数据丢失、无法退出、无法恢复或静默重复执行问题。

## P1：真实用户验证与日常体验

### 验证目标

- 招募 20 至 30 名经常使用 Codex Desktop 的用户，macOS 与 Windows 各至少 5 次有效安装尝试。
- 安装成功率不低于 80%，成功安装后的激活率不低于 50%。
- 至少 5 名用户在 7 天内再次打开并推进任务。
- 至少 5 名用户能不经解释说出 Better Codex 解决的问题。
- 所有失败归类为安装、兼容、认知、功能或体验问题。

### 优先处理

1. 安装、启动、Runtime、注入和会话恢复失败。
2. 状态误判、消息重复、消息丢失、无法中断和无法继续。
3. 用户不知道如何创建第一张 Issue、如何分配 Agent、如何审核和如何返回会话。
4. 最后才处理不影响核心闭环的视觉与偏好问题。

## P2：Self-hosted Hub 与 Web UI

当前优先实施自托管方案，不先建设 Better Codex 官方账号、OAuth 和托管云服务。

推荐顺序：

1. 合入本地 Web UI，并让真实浏览器承担共享功能的自动化调试。
2. 建立 Web E2E、故障注入、证据产物和 CI 门禁，只保留最小 Codex 安装态人工冒烟。
3. 实现本机权威、远端只读投影和单 writer device。
4. 增加远程命令、幂等确认、版本冲突和离线恢复。
5. 完成公网认证、HTTPS、备份、恢复和跨平台发布门禁。

完整阶段、测试矩阵和验收标准见 [Self-hosted Hub 与 Web UI 实施计划](modules/PLAN_SELF_HOSTED_WEBUI.md)。

## P3 与 P4：持续发布和能力扩展

- 公开发布已经发生，后续重点是稳定 Release、安装入口、文档、兼容声明和真实反馈处理。
- 多 Agent 不再等待前置阶段才开始开发，但必须在 P0 稳定状态模型上完成并发、恢复和人工审核验收。
- 独立 Web UI 已进入 P2：它既是注入故障时的降级入口，也是共享功能自动化调试的主要宿主。
- 图式工作流只在重复、可验证的多步骤流程需求出现后启动，不抢占 Session 与发布稳定性工作。

## 明确不做

- 不在 P0 期间增加团队空间、组织权限、云端远程执行或通用模型供应商。
- 不同步 Codex 对话正文、代码仓库、本地文件、附件、日志和环境变量。
- 不直接复制 SQLite 文件做多端同步。
- 不用更多状态、节点或 Agent 数量代替可靠性与用户验证。
- 不把 Preview CI、源码检查或 Mockup 结果当作真实桌面验收。

## 计划维护规则

- 本文件是当前执行入口；旧 `PLAN_1.x`、`PLAN_3_OFFICIAL_MCP_SYNC.md` 和早期 `phases/` 文件只作为历史设计参考。
- 每次 Stable 发布、架构边界变化或阶段门槛达成后更新一次。
- 看板只记录可执行任务，本路线图记录顺序、依赖、范围和验收。
- 未完成真实验收的事项不能因为代码存在或 Agent 回复完成而在本文件中标为完成。
