# Plan 3.2：需求到贡献闭环

## 目标

把真实 Codex 用户痛点转化为可追踪、可认领、可验收的贡献任务，逐步形成社区，而不是预先制造社区规模。

## 范围

- 建立 Codex Pain Map，记录痛点来源、影响、Better Codex 状态和关联 Issue。
- 将私测与公开反馈分类为 Bug、兼容、体验、功能和不在范围。
- 只有复现或确认价值的问题才进入 Roadmap。
- 为适合外部贡献的问题补充原因、范围、验收条件、相关模块和预计投入。
- 使用少量清晰标签标记难度、平台和领域。
- Release Notes 署名代码与非代码贡献。
- 当持续讨论已经形成后再评估独立社区渠道。

## 不包含

- 固定凑满 20 个 Issue。
- 用 Founding Contributor 身份替代贡献质量判断。
- 自动把所有 Codex 投诉承诺为产品功能。
- 首发前创建 Discord 或复杂贡献积分体系。

## 验收

- Pain Map 的每个条目都有来源、状态和最后核验时间。
- 每个 `good first issue` 能由陌生贡献者独立完成并验证。
- 外部 PR 能关联真实问题和明确验收条件。
- 已拒绝或暂缓的需求有清楚边界，避免重复讨论。
- 发布说明能正确感谢代码、复现、设计、文档和社区支持贡献。

## 回滚

暂停贡献活动不影响产品发布和用户数据；错误条目通过状态修正而不是删除历史来源。
